# 国产化大模型推理 Benchmark 方案总结

> 日期：2026-05-11  
> 背景：围绕甲方提出的两个大模型推理场景，乙方需要基于国产化 AI 服务器完成 Benchmark 验证，输出可复现的测试方法、测试数据、方案对比和推荐配置，供甲方后续内部评估与线上复测使用。

---

## 1. 项目定位

本项目的核心不是“搭一个推理服务”或“跑通一个 Demo”，而是帮助甲方建立一套面向国产化 AI 服务器的大模型推理能力评估基线。

更准确地说，这是一个 **国产化大模型推理方案选型与 Benchmark 验证项目**。

本次工作的重点包括：

- 基于甲方真实业务场景，定义可测试、可复现的 workload；
- 在国产化服务器上验证不同模型、不同部署方式、不同资源配置下的实际表现；
- 分别评估吞吐型任务和在线交互型任务的能力边界；
- 输出甲方可以复测、可以对比、可以用于后续选型的数据；
- 为甲方后续线上验证、资源采购和架构定型提供依据。

乙方的价值不在于替甲方直接下结论，而在于把测试方法、测试数据和方案边界讲清楚，让甲方后续可以基于同一套口径继续验证。

## 3. 两个核心测试场景

目前项目可以明确拆分为两个测试场景：

1. 多模态数据生成 / 多模态推理场景；
2. Agent / OpenClaw 风格在线交互场景。

两个场景都要求使用国产化 AI 服务器，但二者的业务目标、核心指标和测试方法完全不同，不能用同一套标准简单评价。

---

## 4. 场景一：多模态数据生成 / 推理

### 4.1 场景定义

场景一主要面向多模态数据生成和长上下文推理任务。

该场景的典型特点是：

- 输入可能包含文本、图片、视频；
- 可能存在多轮上下文；
- 输入 + 输出整体按小于 64k tokens 对齐；
- 极限 case 可能接近 32k 输入 + 32k 输出；
- 输出较长，单条任务执行时间可能较长；
- 客户对单请求时延不敏感，更关注整体数据生成效率。

这个场景本质上是“吞吐优先”的离线或准离线任务，不应按在线 Chat 的体验指标作为主要评价标准。

### 4.2 候选模型

当前理解下，适合该场景的模型主要包括：

- Kimi 2.6；
- Qwen3.5-397B。

原因是这类模型更适合处理多模态输入、长上下文和长输出，更符合数据生成任务的负载特征。

### 4.3 优化目标

该场景不强关注在线 SLA。

TTFT 和 TPOT 可以适当放宽，单请求耗时较长、任务排队、异步处理都可以接受。

真正需要优化的是：

- 单位时间内可以完成多少条数据生成任务；
- 每小时或每天可以生成多少 tokens；
- 国产化服务器的 GPU/NPU 利用率是否能拉满；
- 长上下文、长输出场景是否稳定；
- 单 token 成本是否具备经济性；
- 在 PD 分离、batch 调度、cache 策略优化后，吞吐能提升多少。

### 4.4 关键指标

建议优先关注以下指标：

| 指标 | 说明 |
|---|---|
| TPM | Tokens Per Minute，核心吞吐指标 |
| 每小时样本数 | 更贴近业务侧的数据生成能力 |
| GPU/NPU 利用率 | 判断国产化硬件是否被充分利用 |
| HBM / 显存占用 | 判断长上下文和 KV Cache 压力 |
| Batch 扩展能力 | 判断扩大 batch 后吞吐是否继续提升 |
| 长输出稳定性 | 观察 16k/32k 输出过程中是否掉速或失败 |
| OOM 率 | 判断极限上下文下的稳定性 |
| 成功率 | 判断是否具备生产可用性 |
| 每百万 tokens 成本 | 用于 ROI 和资源规划 |

TTFT 和 TPOT 仍建议记录，但在该场景下不应作为第一优先级指标。

### 4.5 需要甲方提供的输入

为了保证 Benchmark 数据对甲方真实生产有参考价值，需要甲方提供真实数据集或 workload 画像。

建议收集以下信息：

- 输入 token 长度分布：AVG / P50 / P95 / P99；
- 输出 token 长度分布：AVG / P50 / P95 / P99；
- 文本、图片、视频输入占比；
- 图片数量、尺寸和典型格式；
- 视频时长、分辨率、FPS、抽帧策略；
- 多轮上下文平均轮次；
- 每日或每批次需要生成的数据量；
- 任务完成时间窗口，例如 8 小时内完成还是 24 小时内完成；
- 是否允许排队；
- 是否允许异步返回；
- 失败后是否允许重试；
- 输出结果是否需要二次质量校验。

这些输入决定了测试是否能代表真实 workload。否则，如果只用乙方自构造 prompt，测试结果很可能与甲方线上表现不一致。

### 4.6 建议测试设计

建议按照长度和模态组合设计测试 case：

| Case | 输入 | 输出 | 目的 |
|---|---|---|---|
| S | 4k | 4k | 基础能力验证 |
| M | 16k | 8k / 16k | 中等长上下文验证 |
| L | 32k | 32k | 极限长上下文 + 长输出验证 |
| MM-Image | 图片 + 文本 | 长文本 | 图文多模态生成验证 |
| MM-Video | 视频 + 文本 | 长文本 | 视频理解与数据生成验证 |

测试过程中重点观察：

- 不同 batch size 下的吞吐曲线；
- 长输出过程中 TPOT 是否随时间衰减；
- KV Cache 是否出现碎片化或调度抖动；
- 显存 / HBM 是否成为瓶颈；
- visual encoder 是否成为多模态推理瓶颈；
- 是否需要 Prefill / Decode 分离；
- PD 分离前后吞吐提升比例。

## 5. 场景二：Agent / OpenClaw 风格在线交互

### 5.1 场景定义

场景二是典型的在线 Agent 交互模式，也可以理解为“龙虾模式”：用户输入任务，Agent 进行推理、工具调用、工作流编排，再将结果返回给用户。

该场景的典型特点是：

- 用户在线等待模型响应；
- 首 token 返回速度影响用户体感；
- 可能存在多轮对话；
- 可能涉及工具调用、MCP、API 调用或工作流编排；
- 需要关注并发压力下的 P50 / P95 / P99 表现；
- 不是简单追求最大吞吐，而是追求在线体验和并发承载能力之间的平衡。

### 5.2 候选模型

当前理解下，该场景主要使用：

- GLM5.1；
- DSV4。

这两个模型在该场景中不需要处理图片或视频输入，主要用于 Agent 对话、推理、工具调用和工作流编排。

### 5.3 优化目标

该场景的核心目标是保障在线交互体验。

重点包括：

- TTFT 足够快，用户能尽快看到首 token；
- TPOT 足够稳定，流式输出不能明显卡顿；
- 并发上来后 P95 / P99 时延不能快速恶化；
- 多轮上下文增长后仍能稳定运行；
- 工具调用链路的端到端时延可控；
- Cache 命中后能显著改善 TTFT 和整体响应时间。

### 5.4 关键指标

建议优先关注以下指标：

| 指标 | 说明 |
|---|---|
| TTFT P50 / P95 / P99 | 首 token 响应体验 |
| TPOT P50 / P95 / P99 | 流式输出顺滑度 |
| P95 总响应时间 | 用户侧整体等待时间 |
| 并发能力 | 在线请求承载能力 |
| Queue Delay | 判断排队是否成为瓶颈 |
| Cache 命中率 | 衡量上下文复用收益 |
| Tool Calling Latency | 衡量 Agent 工具链开销 |
| 成功率 | 衡量 Agent 任务稳定性 |
| TPS / TPM | 辅助评估总体吞吐 |
| GPU/NPU 利用率 | 判断资源利用效率 |

### 5.5 需要甲方提供的输入

该场景不能只说“体验要好”，必须转化为可测试的 SLA 指标。

建议甲方补充以下信息：

- TTFT 目标，例如 ≤3s 或 ≤5s；
- TPOT 目标，例如 ≤50ms 或 ≤100ms；
- P95 总响应时间目标；
- 峰值并发请求数；
- 同时在线用户数；
- 每个任务平均对话轮次；
- 每轮平均输入 tokens 和输出 tokens；
- 工具调用比例；
- 每个任务平均工具调用次数；
- 是否要求流式输出；
- 预期 Cache 命中率；
- System Prompt 和 Tool Schema 是否固定；
- 是否存在长上下文复用。

这些信息决定了测试目标和压测方式。如果没有明确 SLA，测试结果很难判断“好”还是“不好”。

### 5.6 建议测试设计

建议将 Agent 测试拆成以下几类：

| Case | 说明 | 目的 |
|---|---|---|
| 单轮 Chat | 无工具调用 | 建立基础 TTFT / TPOT baseline |
| 多轮 Chat | 5-10 轮上下文 | 观察 KV Cache 增长后的性能变化 |
| 单工具调用 | 每轮一次工具调用 | 测量工具链开销 |
| 多工具调用 | 多工具组合和工作流编排 | 测量 Agent Runtime 开销 |
| Cache 关闭 | 不使用上下文缓存 | 建立无 cache baseline |
| 50% Cache 命中 | 部分上下文复用 | 测量 cache 收益 |
| 80% Cache 命中 | 高比例上下文复用 | 测量较优 cache 条件下的性能 |
| 并发阶梯压测 | 10 / 50 / 100 / 200 并发 | 找到并发能力边界和崩塌点 |

Agent 场景不应只测单轮 Chat。真正有价值的是测多轮、工具调用、cache 命中和并发压力下的 P95/P99 变化。

## 6. 两个场景的核心差异

| 维度 | 场景一：多模态数据生成 | 场景二：Agent 在线交互 |
|---|---|---|
| 业务形态 | 离线 / 准离线数据生成 | 在线交互 |
| 候选模型 | Kimi2.6 / Qwen3.5-397B | GLM5.1 / DSV4 |
| 多模态输入 | 需要 | 不需要 |
| SLA 敏感度 | 低 | 高 |
| 核心指标 | TPM、每小时样本数、利用率、成本 | TTFT、TPOT、P95 时延、并发 |
| 排队 | 可以接受 | 需要控制 |
| 异步执行 | 可以接受 | 通常不适合作为主交互链路 |
| 输出长度 | 可能很长 | 通常中等，取决于任务 |
| Cache 价值 | 高，主要提升吞吐 | 很高，直接影响体验 |
| PD 分离价值 | 高 | 取决于上下文长度和并发压力 |
| 测试重点 | 吞吐上限和长稳能力 | 在线 SLA 和并发边界 |

## 7. 对王磊提出指标的理解

王磊提到的指标包括：

- 业务数据集输入 / 输出长度的 AVG、P50、P99；
- TTFT；
- TPOT；
- 并发需求；
- Cache 命中率。

这些指标都很重要，但需要按场景区分优先级。

| 指标 | 场景一 | 场景二 |
|---|---|---|
| 输入长度 AVG/P50/P99 | 用于吞吐和显存规划 | 用于 SLA 和上下文压力评估 |
| 输出长度 AVG/P50/P99 | 非常关键，决定 decode 占卡时间 | 重要，直接影响用户等待时间 |
| TTFT | 记录即可，不是主要优化目标 | 核心 SLA 指标 |
| TPOT | 记录并观察长输出衰减 | 核心体验指标 |
| 并发 | 更接近批量任务并行度 | 核心在线承载能力指标 |
| Cache 命中率 | 降低 prefill 成本，提升吞吐 | 改善 TTFT、多轮体验和整体响应时间 |

## 8. Benchmark 方法论

为了让测试结果具备可信度，必须统一 Benchmark 方法论。

### 8.1 统一测试输入

测试输入不能只依赖 Demo Prompt，应尽量使用甲方真实数据集或具有代表性的抽样 workload。

场景一的数据集应覆盖：

- 纯文本输入；
- 图片 + 文本输入；
- 视频 + 文本输入；
- 多轮上下文；
- 不同输入 / 输出长度档位。

场景二的数据集应覆盖：

- 单轮问答；
- 多轮问答；
- 工具调用；
- 长 System Prompt；
- 不同 Cache 命中率设置。

### 8.2 统一指标字段

建议测试数据统一记录以下字段：

```text
model
server_type
deployment_mode
tp_size
pp_size
batch_size
concurrency
input_tokens_avg
input_tokens_p50
input_tokens_p95
input_tokens_p99
output_tokens_avg
output_tokens_p50
output_tokens_p95
output_tokens_p99
ttft_avg
ttft_p50
ttft_p95
ttft_p99
tpot_avg
tpot_p50
tpot_p95
tpot_p99
throughput_tps
throughput_tpm
samples_per_hour
gpu_or_npu_util
hbm_util
kv_cache_usage
cache_hit_rate
success_rate
oom_count
error_count
cost_per_million_tokens
```

### 8.3 统一测试时长

不建议只跑几分钟 peak 数据。

建议至少包含三类测试：

- 冒烟测试：5-10 分钟，用于快速验证环境和链路；
- 标准压测：30 分钟，用于观察稳定吞吐；
- 长稳测试：1 小时或更长，用于观察掉速、内存碎片、调度抖动和错误率。

### 8.4 统一流量模型

建议支持以下压测方式：

- 固定并发；
- 阶梯式并发提升；
- Burst 突发流量；
- 接近真实业务流量的到达模型。

不同流量模型下的数据要分开记录，避免混在一起比较。

## 9. 国产化 AI 服务器测试重点

由于两个场景都要求使用国产化 AI 服务器，本次 Benchmark 需要特别关注国产化硬件在大模型推理中的真实瓶颈。

重点包括：

- 大模型是否可以稳定加载和运行；
- 多卡并行效率是否达标；
- HBM / 显存容量边界；
- 长上下文下 KV Cache 压力；
- 32k 输出过程中是否出现性能衰减；
- 多模态场景中 visual encoder 是否成为瓶颈；
- PD 分离是否能带来稳定收益；
- 高并发下 TTFT 是否快速恶化；
- 工具调用是否明显拉长端到端 SLA；
- 长稳测试中是否出现掉速、错误、OOM 或调度抖动。

国产化服务器测试的价值不只是证明“能跑”，而是要说明：

- 在什么 workload 下跑得最好；
- 性能边界在哪里；
- 哪些指标会先崩；
- 哪些优化手段有效；
- 哪些风险需要甲方线上复测时重点关注。

## 12. 一句话总结

本项目应采用 **workload-driven + SLA-driven** 的测试方法：

- 场景一用真实多模态数据集，测试国产化 AI 服务器的数据生成吞吐上限和长稳能力；
- 场景二用明确的 Agent SLA，测试国产化 AI 服务器的在线交互体验和并发边界；
- 最终输出一套可复现、可对比、可供甲方线上验证的国产化大模型推理能力基线。
