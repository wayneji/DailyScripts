# 国产化大模型推理 Benchmark 方案总结

> 日期：2026-05-11  
> 背景：乙方团队需要基于国产化 AI 服务器，对甲方两个典型大模型推理场景进行 Benchmark 测试，并输出可复现测试数据、推荐配置，以及供甲方后续线上验证使用的依据。

---

## 1. 项目定位

本项目不是简单建设一个推理平台，也不是单纯跑通一个 Demo，而是更接近一个 **国产化大模型推理方案选型与 Benchmark 验证项目**。

核心目标是帮助甲方建立一套面向国产化 AI 服务器的大模型推理能力基线。

关键目标包括：

- 明确不同业务负载下国产化服务器的推理能力边界；
- 对比不同模型、不同部署模式、不同资源配置下的吞吐、SLA 和稳定性表现；
- 形成可复现的 Benchmark 方法和测试数据；
- 为甲方后续线上验证、方案选型和采购评估提供推荐配置和数据依据。

乙方的价值不是替甲方直接做最终决策，而是为甲方提供可信、可对比、可复现的 Benchmark 证据。

## 2. 角色定义

当前角色关系如下：

- 王磊 / 乙方团队：负责 Benchmark 设计、测试执行、数据采集和方案建议输出；

---

## 3. 两个核心场景

当前项目可以拆分为两个主要场景：

1. 多模态数据生成 / 多模态推理；
2. Agent / OpenClaw 风格在线交互。

两个场景都要求使用国产化 AI 服务器，但两者的优化目标和 Benchmark 指标完全不同。

---

## 4. 场景一：多模态数据生成 / 推理

### 4.1 场景定义

场景一主要面向数据生成和多模态推理任务。

典型业务特征包括：

- 输入可能包含文本、图片和视频；
- 可能存在多轮上下文；
- 输入 + 输出整体按照小于 64k tokens 对齐；
- 极限情况可能接近 32k 输入 + 32k 输出；
- 输出可能较长；
- 单任务时延可以相对较长；
- 核心目标是吞吐能力，而不是单请求低时延。

### 4.2 候选模型

当前理解：

- Kimi 2.6；
- Qwen3.5-397B。

这两个模型更适合多模态数据生成场景，因为它们预期支持原生多模态输入和长上下文生成。

### 4.3 优化目标

该场景对在线 SLA 不高度敏感。

TTFT 和 TPOT 可以适当放宽。单请求执行时间较长、排队和异步任务执行都可能是可接受的。

真正优先关注的是：

- 每小时或每天可以生成多少条样本；
- 每分钟或每小时可以生成多少 tokens；
- GPU/NPU 利用率是否足够高；
- 长上下文和长输出任务是否稳定；
- 单 token 成本是否可接受。

### 4.4 关键指标

建议优先关注以下指标：

| 指标 | 说明 |
|---|---|
| TPM | Tokens per minute，核心吞吐指标 |
| 每小时样本数 | 业务侧数据生成能力 |
| GPU/NPU 利用率 | 判断硬件是否被高效使用 |
| HBM / 显存占用 | 长上下文和 KV Cache 压力 |
| Batch 扩展能力 | 判断是否能通过更大 batch 提升吞吐 |
| 长输出稳定性 | 判断 16k/32k 输出是否稳定 |
| OOM 率 | 极限上下文长度下的稳定性 |
| 成功率 | 生产可用性 |
| 每百万 tokens 成本 | ROI 和资源规划参考 |

TTFT 和 TPOT 仍然建议记录，但不是该场景的第一优先级优化目标。

### 4.5 需要甲方提供的输入

为了让 Benchmark 贴近真实生产负载，甲方需要提供数据集或 workload 画像。

需要的信息包括：

- 输入 token 分布：AVG / P50 / P95 / P99；
- 输出 token 分布：AVG / P50 / P95 / P99；
- 文本、图片、视频输入的比例；
- 图片数量和典型图片规格；
- 视频时长、分辨率、FPS 和抽帧策略；
- 多轮上下文平均轮次；
- 总任务量，例如每日生成目标；
- 完成时间窗口，例如 8 小时或 24 小时；
- 是否允许排队；
- 是否允许异步返回；
- 失败后是否允许重试；
- 输出质量是否需要二次校验。

### 4.6 建议测试设计

建议测试用例如下：

| Case | 输入 | 输出 | 目的 |
|---|---|---|---|
| S | 4k | 4k | 基础能力测试 |
| M | 16k | 8k / 16k | 中等长上下文测试 |
| L | 32k | 32k | 极限长上下文 + 长输出测试 |
| MM-Image | 图片 + 文本 | 长文本 | 多模态图文生成测试 |
| MM-Video | 视频 + 文本 | 长文本 | 视频理解与数据生成测试 |

测试过程中需要重点观察：

- 不同 batch size 下的吞吐曲线；
- 长输出过程中 TPOT 是否衰减；
- 是否出现 KV Cache 碎片化或调度抖动；
- 显存 / 内存容量是否成为瓶颈；
- 是否需要 Prefill/Decode 分离；
- PD 分离前后的吞吐提升比例。

## 5. 场景二：Agent / OpenClaw 风格在线交互

### 5.1 场景定义

场景二是典型的在线 Agent 交互负载。

典型业务特征包括：

- 用户在线等待模型响应；
- 首 token 快速返回非常重要；
- 可能存在多轮对话；
- 可能涉及工具调用、MCP、API 调用或工作流编排；
- 用户体验对等待时间敏感；
- 需要关注 P50 / P95 / P99 时延。

该场景不能只优化最大吞吐，而应在在线体验和并发承载能力之间取得平衡。

### 5.2 候选模型

当前理解：

- GLM5.1；
- DSV4。

这两个模型在该场景下不需要处理图片或视频输入，主要用于 Agent 对话、工具调用、推理和工作流编排。

### 5.3 优化目标

关键目标包括：

- TTFT 足够快；
- 流式输出足够顺滑；
- 并发压力下 P95 / P99 时延保持稳定；
- 多轮上下文处理稳定；
- 端到端工具调用时延可控；
- 在 cache 命中率较高时可以获得明显性能收益。

### 5.4 关键指标

建议优先关注以下指标：

| 指标 | 说明 |
|---|---|
| TTFT P50 / P95 / P99 | 首 token 用户体验 |
| TPOT P50 / P95 / P99 | 流式输出顺滑度 |
| P95 总响应时间 | 端侧用户等待体验 |
| 并发能力 | 在线请求承载能力 |
| Queue delay | 判断排队是否成为瓶颈 |
| Cache 命中率 | 上下文复用收益 |
| Tool calling latency | Agent 工具链开销 |
| 成功率 | Agent 任务稳定性 |
| TPS / TPM | 辅助吞吐指标 |
| GPU/NPU 利用率 | 硬件效率 |

### 5.5 需要甲方提供的输入

甲方需要提供清晰的 SLA 目标和 workload 假设。

需要的信息包括：

- TTFT 目标，例如 <= 3s 或 <= 5s；
- TPOT 目标，例如 <= 50ms 或 <= 100ms；
- P95 总响应时间目标；
- 峰值并发请求数；
- 同时在线用户数；
- 每个任务平均对话轮次；
- 每轮平均输入和输出 tokens；
- 工具调用比例；
- 每个任务平均工具调用次数；
- 是否要求流式输出；
- 预期 Cache 命中率；
- System prompt 和 tool schema 是否固定；
- 是否存在长上下文复用。

### 5.6 建议测试设计

建议测试用例如下：

| Case | 说明 | 目的 |
|---|---|---|
| 单轮 Chat | 无工具调用 | 测量基础 TTFT / TPOT |
| 多轮 Chat | 5-10 轮 | 测量 KV Cache 增长后的性能 |
| 单工具调用 | 每轮一次工具 | 测量工具链开销 |
| 多工具调用 | 多工具和工作流编排 | 测量 Agent Runtime 开销 |
| Cache 关闭 | 无上下文缓存 | 建立 baseline |
| 50% Cache 命中 | 部分复用 | 测量 Cache 收益 |
| 80% Cache 命中 | 高复用 | 测量较优场景下的 Cache 收益 |
| 并发阶梯压测 | 10 / 50 / 100 / 200 并发 | 找到性能崩塌点 |

测试不应只覆盖单轮 Chat，还应覆盖多轮上下文、工具调用，以及并发下的 P95/P99 表现。

## 6. 两个场景的核心差异

| 维度 | 场景一：多模态数据生成 | 场景二：Agent 在线交互 |
|---|---|---|
| 业务形态 | 离线 / 准离线生成 | 在线交互 |
| 候选模型 | Kimi2.6 / Qwen3.5-397B | GLM5.1 / DSV4 |
| 多模态输入 | 需要 | 不需要 |
| SLA 敏感度 | 低 | 高 |
| 核心指标 | TPM、每小时样本数、利用率、成本 | TTFT、TPOT、P95 时延、并发 |
| 排队 | 可接受 | 需要控制 |
| 异步执行 | 可接受 | 通常不适合主交互链路 |
| 输出长度 | 可能很长 | 通常中等，取决于任务 |
| Cache 价值 | 高，提升吞吐 | 很高，提升体验 |
| PD 分离价值 | 高 | 取决于上下文长度和并发 |
| 测试重点 | 吞吐极限和稳定性 | 在线 SLA 和并发边界 |

## 7. 对王磊指标问题的理解

王磊提到的指标包括：

- 业务数据集输入 / 输出长度：AVG / P50 / P99；
- TTFT；
- TPOT；
- 并发需求；
- Cache 命中率。

这些指标需要按场景分别理解。

| 指标 | 场景一 | 场景二 |
|---|---|---|
| 输入长度 AVG/P50/P99 | 用于吞吐和显存规划 | 用于 SLA 和上下文压力评估 |
| 输出长度 AVG/P50/P99 | 非常重要，决定 decode 时长 | 重要，影响用户等待时间 |
| TTFT | 记录即可，不是主要优化目标 | 核心 SLA 指标 |
| TPOT | 记录并观察长输出衰减 | 核心用户体验指标 |
| 并发 | 更像批量任务并行度 | 核心在线承载能力指标 |
| Cache 命中率 | 提升吞吐并降低 prefill 成本 | 提升 TTFT 和多轮体验 |

## 8. Benchmark 方法论

为了让 Benchmark 结果对甲方可信，需要统一测试方法论。

### 8.1 统一测试输入

不能只依赖 Demo Prompt，Benchmark 应尽量使用甲方真实或有代表性的 workload 样本。

场景一的数据集应包括：

- 纯文本输入；
- 图片 + 文本输入；
- 视频 + 文本输入；
- 多轮上下文；
- 不同输入和输出长度档位。

场景二的数据集应包括：

- 单轮问答；
- 多轮问答；
- 工具调用；
- 长 system prompt；
- 不同 Cache 命中率设置。

### 8.2 统一指标字段

建议记录字段如下：

```text
model
server_type
deployment_mode
tp_size
pp_size
batch_size
concurrency
input_tokens_avg
input_tokens_p50
input_tokens_p95
input_tokens_p99
output_tokens_avg
output_tokens_p50
output_tokens_p95
output_tokens_p99
ttft_avg
ttft_p50
ttft_p95
ttft_p99
tpot_avg
tpot_p50
tpot_p95
tpot_p99
throughput_tps
throughput_tpm
samples_per_hour
gpu_or_npu_util
hbm_util
kv_cache_usage
cache_hit_rate
success_rate
oom_count
error_count
cost_per_million_tokens
```

### 8.3 统一测试时长

不建议只依赖短时间 peak 测试。

推荐测试时长包括：

- 冒烟测试：5-10 分钟，用于快速验证；
- 标准压测：30 分钟，用于观察稳定吞吐；
- 长稳测试：1 小时或更长，用于观察性能衰减、内存碎片和调度抖动。

### 8.4 统一流量模型

推荐流量模式包括：

- 固定并发；
- 阶梯式并发提升；
- Burst 突发流量；
- 接近真实生产业务的到达模型。

## 9. 国产化 AI 服务器测试重点

由于两个场景都要求使用国产化 AI 服务器，Benchmark 需要重点关注实际瓶颈。

关键关注点包括：

- 大模型是否可以稳定加载和运行；
- 多卡并行效率；
- HBM / 显存容量边界；
- 长上下文下 KV Cache 压力；
- 32k 输出是否导致性能衰减；
- 多模态 workload 中 visual encoder 是否成为瓶颈；
- PD 分离是否带来稳定收益；
- 高并发下 TTFT 是否快速恶化；
- 工具调用是否影响端到端 SLA；
- 长稳测试是否暴露性能衰减、错误、OOM 或调度抖动。

Benchmark 的价值不只是证明模型“能跑”，更重要的是识别它在哪类负载下跑得最好、边界在哪里、还存在哪些风险。

## 10. 推荐交付物

### 10.1 测试方案文档

应包括：

- 背景；
- 场景定义；
- 模型范围；
- 硬件范围；
- 指标体系；
- 测试方法；
- 数据集说明；
- 测试环境说明。

### 10.2 Benchmark 数据表

应包括：

- 场景一多模态数据生成吞吐结果；
- 场景二 Agent SLA 和并发结果；
- 不同国产服务器之间的横向对比；
- 不同部署模式之间的对比；
- PD 分离前后对比；
- Cache 命中率对比。

### 10.3 推荐方案

针对每个场景分别给出：

- 推荐模型；
- 推荐国产服务器配置；
- 推荐部署模式；
- 推荐并发或 batch 设置；
- 推荐 cache 策略；
- 是否推荐 PD 分离；
- 预期吞吐或 SLA；
- 主要风险和适用边界。

### 10.4 甲方线上验证指南

应包括：

- 如何复现乙方 Benchmark 结果；
- 线上验证时需要采集哪些指标；
- 哪些 Benchmark 结果可以直接参考；
- 哪些结果需要结合真实生产流量重新校准。

## 12. 一句话总结

本项目应采用 **workload-driven + SLA-driven** 的 Benchmark 方法：

- 场景一使用真实多模态数据集，测试国产化 AI 服务器的最大数据生成吞吐；
- 场景二使用明确的 Agent SLA 目标，测试国产化 AI 服务器的在线交互能力边界；
- 最终输出应是一套可复现、可对比、可供甲方验证的国产化大模型推理能力基线。
