# 国产化大模型推理 Benchmark 方案总结

> 日期：2026-05-11  
> 背景：围绕甲方提出的两个大模型推理场景，乙方需要基于国产化 AI 服务器完成 Benchmark 验证，输出可复现的测试方法、测试数据、方案对比和推荐配置，供甲方后续内部评估与线上复测使用。

---

## 1. 项目定位

本项目的核心不是“搭一个推理服务”或“跑通一个 Demo”，而是帮助甲方建立一套面向国产化 AI 服务器的大模型推理能力评估基线。

更准确地说，这是一个 **国产化大模型推理方案选型与 Benchmark 验证项目**。

本次工作的重点包括：

- 基于甲方真实业务场景，定义可测试、可复现的 workload；
- 在国产化服务器上验证不同模型、不同部署方式、不同资源配置下的实际表现；
- 分别评估吞吐型任务和在线交互型任务的能力边界；
- 输出甲方可以复测、可以对比、可以用于后续选型的数据；
- 为甲方后续线上验证、资源采购和架构定型提供依据。

乙方的价值不在于替甲方直接下结论，而在于把测试方法、测试数据和方案边界讲清楚，让甲方后续可以基于同一套口径继续验证。

## 3. 两个核心测试场景

目前项目可以明确拆分为两个测试场景：

1. 多模态数据生成 / 多模态推理场景；
2. 长程 Agent / Code Search / OpenClaw 风格在线交互场景。

两个场景都要求使用国产化 AI 服务器，但二者的业务目标、核心指标和测试方法完全不同，不能用同一套标准简单评价。

---

## 4. 场景一：多模态数据生成 / 推理

### 4.1 场景定义

场景一主要面向多模态数据生成和长上下文推理任务。

该场景的典型特点是：

- 输入可能包含文本、图片、视频；
- 可能存在多轮上下文；
- 输入 + 输出整体按小于 64k tokens 对齐；
- 极限 case 可能接近 32k 输入 + 32k 输出；
- 输出较长，单条任务执行时间可能较长；
- 客户对单请求时延不敏感，更关注整体数据生成效率。

这个场景本质上是“吞吐优先”的离线或准离线任务，不应按在线 Chat 的体验指标作为主要评价标准。

### 4.2 候选模型

当前理解下，适合该场景的模型主要包括：

- Kimi 2.6；
- Qwen3.5-397B。

原因是这类模型更适合处理多模态输入、长上下文和长输出，更符合数据生成任务的负载特征。

### 4.3 优化目标

该场景不强关注在线 SLA。

TTFT 和 TPOT 可以适当放宽，单请求耗时较长、任务排队、异步处理都可以接受。

真正需要优化的是：

- 单位时间内可以完成多少条数据生成任务；
- 每小时或每天可以生成多少 tokens；
- 国产化服务器的 GPU/NPU 利用率是否能拉满；
- 长上下文、长输出场景是否稳定；
- 单 token 成本是否具备经济性；
- 在 PD 分离、batch 调度、cache 策略优化后，吞吐能提升多少。

### 4.4 关键指标

建议优先关注以下指标：

| 指标 | 说明 |
|---|---|
| TPM | Tokens Per Minute，核心吞吐指标 |
| 每小时样本数 | 更贴近业务侧的数据生成能力 |
| GPU/NPU 利用率 | 判断国产化硬件是否被充分利用 |
| HBM / 显存占用 | 判断长上下文和 KV Cache 压力 |
| Batch 扩展能力 | 判断扩大 batch 后吞吐是否继续提升 |
| 长输出稳定性 | 观察 16k/32k 输出过程中是否掉速或失败 |
| OOM 率 | 判断极限上下文下的稳定性 |
| 成功率 | 判断是否具备生产可用性 |
| 每百万 tokens 成本 | 用于 ROI 和资源规划 |

TTFT 和 TPOT 仍建议记录，但在该场景下不应作为第一优先级指标。

### 4.5 需要甲方提供的输入

为了保证 Benchmark 数据对甲方真实生产有参考价值，需要甲方提供真实数据集或 workload 画像。

建议收集以下信息：

- 输入 token 长度分布：AVG / P50 / P95 / P99；
- 输出 token 长度分布：AVG / P50 / P95 / P99；
- 文本、图片、视频输入占比；
- 图片数量、尺寸和典型格式；
- 视频时长、分辨率、FPS、抽帧策略；
- 多轮上下文平均轮次；
- 每日或每批次需要生成的数据量；
- 任务完成时间窗口，例如 8 小时内完成还是 24 小时内完成；
- 是否允许排队；
- 是否允许异步返回；
- 失败后是否允许重试；
- 输出结果是否需要二次质量校验。

这些输入决定了测试是否能代表真实 workload。否则，如果只用乙方自构造 prompt，测试结果很可能与甲方线上表现不一致。

### 4.6 建议测试设计

建议按照长度和模态组合设计测试 case：

| Case | 输入 | 输出 | 目的 |
|---|---|---|---|
| S | 4k | 4k | 基础能力验证 |
| M | 16k | 8k / 16k | 中等长上下文验证 |
| L | 32k | 32k | 极限长上下文 + 长输出验证 |
| MM-Image | 图片 + 文本 | 长文本 | 图文多模态生成验证 |
| MM-Video | 视频 + 文本 | 长文本 | 视频理解与数据生成验证 |

测试过程中重点观察：

- 不同 batch size 下的吞吐曲线；
- 长输出过程中 TPOT 是否随时间衰减；
- KV Cache 是否出现碎片化或调度抖动；
- 显存 / HBM 是否成为瓶颈；
- visual encoder 是否成为多模态推理瓶颈；
- 是否需要 Prefill / Decode 分离；
- PD 分离前后吞吐提升比例。

## 5. 场景二：长程 Agent / Code Search / OpenClaw 风格在线交互

### 5.1 场景定义

场景二不是普通 Chat，也不是短上下文问答，而是典型的长程 Agent 场景，重点覆盖 Code / Search 类任务。

该场景可以理解为“龙虾模式”：用户输入任务，Agent 进行多轮推理、搜索、代码理解、工具调用和工作流编排，再将结果返回给用户。

根据甲方最新输入，该场景具有明显长尾特征：

- 输入上下文 P50 约 32k tokens；
- 输入上下文 P99 可能达到 128k-256k tokens；
- Max context 需要拉满到 262k tokens；
- 输出长度 P50 约 8k tokens；
- 输出长度 P99 约 32k-64k tokens；
- Agent 任务轮次很多，多轮上下文会持续增长；
- 需要重点关注长上下文下的吞吐、速度和稳定性。

因此，场景二的核心已经从“普通在线 Agent SLA”升级为：

> 长上下文、多轮、多工具、Code/Search 型长程 Agent 的在线 serving 能力验证。

### 5.2 候选模型

当前理解下，该场景主要使用：

- GLM5.1；
- DSV4。

这两个模型在该场景中不需要处理图片或视频输入，主要用于 Agent 对话、推理、代码理解、搜索增强、工具调用和工作流编排。

### 5.3 最新 SLO / Workload 输入

甲方已补充的关键输入如下：

| 指标 | 当前输入 |
|---|---|
| 典型任务类型 | Code / Search 长程 Agent |
| 输入长度 P50 | 约 32k tokens |
| 输入长度 P99 | 约 128k-256k tokens |
| Max context | 需要支持 262k tokens |
| 输出长度 P50 | 约 8k tokens |
| 输出长度 P99 | 约 32k-64k tokens |
| Agent 轮次 | 多轮，轮次很多 |
| TTFT | 高并发下 P50 < 10s |
| TPOT | 未给明确硬指标，但需要关注长上下文下速度 |
| P99 时延 | 可适当放宽 |
| 排队要求 | 高并发下尽量不要排队 |
| Prefix Cache 命中率 | 当前 benchmark 约 50%，但任务差异较大 |

这组输入说明：

- 该场景输入明显长尾，P99 极长；
- 不能只测 4k/8k/16k 常规上下文；
- 262k max context 是必须验证的能力边界；
- 输出同样存在长尾，32k-64k 输出会显著拉长 decode 占卡时间；
- 高并发下“不排队”意味着必须重点关注调度、KV Cache 容量、并发 admission control 和长请求隔离。

### 5.4 优化目标

该场景仍属于在线交互，但其主要矛盾不是普通 Chat 的低时延，而是：

- 超长上下文下是否能稳定服务；
- 多轮 Agent 任务是否能持续保持速度；
- 高并发下长请求是否导致排队和资源阻塞；
- Prefix Cache 是否能有效降低 prefill 成本；
- 国产化服务器在 128k/256k context 下的 HBM、KV Cache 和调度能力是否足够。

优化目标应包括：

- P50 TTFT 控制在 10s 以内；
- P99 可以放宽，但需要记录并解释长尾原因；
- 高并发下尽量减少排队；
- 关注长上下文 prefill 吞吐；
- 关注长输出 decode 稳定性；
- 关注 Prefix Cache 命中和失效场景的差异；
- 找到国产化服务器在 32k、128k、256k context 下的性能边界。

### 5.5 关键指标

建议优先关注以下指标：

| 指标 | 说明 |
|---|---|
| TTFT P50 / P95 / P99 | 首 token 响应体验，重点看 P50 < 10s 是否满足 |
| TPOT P50 / P95 / P99 | 长输出阶段流式速度 |
| Prefill tokens/s | 长上下文输入处理能力 |
| Decode tokens/s | 长输出阶段生成能力 |
| End-to-end latency P50/P95/P99 | 多轮 Agent 总体响应时间 |
| Queue Delay | 判断高并发是否发生排队 |
| Active KV Cache / HBM 占用 | 判断长上下文并发承载能力 |
| Prefix Cache Hit Rate | 当前参考值约 50%，需分任务统计 |
| Cache Hit vs Miss 性能差异 | 判断 cache 对 TTFT 和吞吐的收益 |
| Long-context success rate | 128k/256k context 下是否稳定 |
| OOM / Eviction / Preemption 次数 | 判断资源边界和调度风险 |
| Agent task success rate | 判断长程任务是否可用 |
| GPU/NPU 利用率 | 判断资源利用效率 |

### 5.6 建议测试设计

建议将场景二从原来的普通 Agent 压测，升级为长上下文 Agent 专项测试。

推荐测试矩阵如下：

| Case | 输入长度 | 输出长度 | 说明 |
|---|---|---|---|
| A1 | 32k | 8k | P50 典型 Agent workload |
| A2 | 64k | 8k / 16k | 中长上下文压力测试 |
| A3 | 128k | 16k / 32k | P99 下沿长尾测试 |
| A4 | 256k | 32k / 64k | 极限长上下文与长输出测试 |
| A5 | 262k max context | 8k / 32k | Max context 能力验证 |
| A6 | 32k，多轮递增 | 8k | 多轮 Agent 上下文增长测试 |
| A7 | 128k，Cache Hit | 16k | Prefix Cache 命中场景 |
| A8 | 128k，Cache Miss | 16k | Prefix Cache 失效场景 |

并发测试建议：

| 并发档位 | 目的 |
|---|---|
| 1 | 单请求能力 baseline |
| 4 / 8 | 小并发下长上下文稳定性 |
| 16 / 32 | 中并发下 queue delay 和 HBM 压力 |
| 64+ | 高并发下是否出现排队、抢占、OOM 或明显长尾 |

测试不应只测平均值，需要重点记录 P95/P99，因为该场景长尾明显。

### 5.7 对方案判断的影响

梁老师这次输入会显著改变场景二的测试重点：

原先如果按普通 Agent 设计，可能重点看 TTFT、TPOT、工具调用和并发；现在必须提升长上下文权重。

具体影响包括：

- 不能只用 4k/8k/16k prompt 做 Agent benchmark；
- 必须验证 128k、256k、262k context；
- Prefill 能力会成为核心瓶颈之一；
- Prefix Cache 的命中率和收益需要单独拆测；
- HBM / KV Cache 容量可能比纯算力更早成为瓶颈；
- 高并发“不排队”在长上下文场景下难度很高，需要测试 admission control 和调度策略；
- PD 分离价值可能明显提升，尤其是长 prefill + 长 decode 的混合负载；
- 推荐方案不能只看单请求速度，要看长上下文并发承载能力。

## 6. 两个场景的核心差异

| 维度 | 场景一：多模态数据生成 | 场景二：长程 Agent / Code Search |
|---|---|---|
| 业务形态 | 离线 / 准离线数据生成 | 在线长程 Agent 交互 |
| 候选模型 | Kimi2.6 / Qwen3.5-397B | GLM5.1 / DSV4 |
| 多模态输入 | 需要 | 不需要 |
| SLA 敏感度 | 低 | 中高，P50 TTFT 有明确目标 |
| 输入长度 | 输入+输出整体 <64k | P50 32k，P99 128k-256k，max 262k |
| 输出长度 | 可能很长 | P50 8k，P99 32k-64k |
| 核心指标 | TPM、每小时样本数、利用率、成本 | TTFT、TPOT、Prefill、KV Cache、Queue Delay |
| 排队 | 可以接受 | 高并发下尽量不要排队 |
| 异步执行 | 可以接受 | 通常不适合作为主交互链路 |
| Cache 价值 | 高，主要提升吞吐 | 很高，直接影响 TTFT 和长上下文成本 |
| PD 分离价值 | 高 | 更高，尤其长 prefill + 长 decode 混合负载 |
| 测试重点 | 吞吐上限和长稳能力 | 长上下文速度、吞吐、并发和稳定性 |

## 7. 对王磊提出指标的理解

王磊提到的指标包括：

- 业务数据集输入 / 输出长度的 AVG、P50、P99；
- TTFT；
- TPOT；
- 并发需求；
- Cache 命中率。

结合甲方最新输入，这些指标已经有了更明确方向。

| 指标 | 场景一 | 场景二 |
|---|---|---|
| 输入长度 AVG/P50/P99 | 用于吞吐和显存规划 | 已明确：P50 32k，P99 128k-256k，max 262k |
| 输出长度 AVG/P50/P99 | 非常关键，决定 decode 占卡时间 | 已明确：P50 8k，P99 32k-64k |
| TTFT | 记录即可，不是主要优化目标 | 高并发下 P50 < 10s，P99 可放宽但必须记录 |
| TPOT | 记录并观察长输出衰减 | 需重点观察长上下文和长输出下的速度 |
| 并发 | 更接近批量任务并行度 | 高并发尽量不排队，需重点测 Queue Delay |
| Cache 命中率 | 降低 prefill 成本，提升吞吐 | 当前参考约 50% Prefix Cache Hit Rate，但需分任务拆测 |

## 8. Benchmark 方法论

为了让测试结果具备可信度，必须统一 Benchmark 方法论。

### 8.1 统一测试输入

测试输入不能只依赖 Demo Prompt，应尽量使用甲方真实数据集或具有代表性的抽样 workload。

场景一的数据集应覆盖：

- 纯文本输入；
- 图片 + 文本输入；
- 视频 + 文本输入；
- 多轮上下文；
- 不同输入 / 输出长度档位。

场景二的数据集应覆盖：

- Code / Search 长程 Agent 任务；
- 32k / 64k / 128k / 256k / 262k context；
- P50 与 P99 两类典型输入长度；
- 8k / 32k / 64k 输出长度；
- 多轮上下文增长；
- Prefix Cache Hit / Miss 对照；
- 高并发下 Queue Delay 和 P99 长尾。

建议测试数据统一记录以下字段：

### 8.3 统一测试时长

不建议只跑几分钟 peak 数据。

建议至少包含三类测试：

- 冒烟测试：5-10 分钟，用于快速验证环境和链路；
- 标准压测：30 分钟，用于观察稳定吞吐；
- 长稳测试：1 小时或更长，用于观察掉速、内存碎片、调度抖动和错误率。

长程 Agent 场景还建议增加：

- 262k max context 单请求稳定性测试；
- 128k/256k 长上下文并发稳定性测试；
- Prefix Cache Hit / Miss 分组测试；
- 多轮 Agent 上下文持续增长测试。

### 8.4 统一流量模型

建议支持以下压测方式：

- 固定并发；
- 阶梯式并发提升；
- Burst 突发流量；
- 接近真实业务流量的到达模型。

不同流量模型下的数据要分开记录，避免混在一起比较。

## 9. 国产化 AI 服务器测试重点

由于两个场景都要求使用国产化 AI 服务器，本次 Benchmark 需要特别关注国产化硬件在大模型推理中的真实瓶颈。

重点包括：

- 大模型是否可以稳定加载和运行；
- 多卡并行效率是否达标；
- HBM / 显存容量边界；
- 长上下文下 KV Cache 压力；
- 128k/256k/262k context 下 prefill 速度和稳定性；
- 32k-64k 输出过程中是否出现性能衰减；
- 多模态场景中 visual encoder 是否成为瓶颈；
- PD 分离是否能带来稳定收益；
- 高并发下 TTFT 和 Queue Delay 是否快速恶化；
- Prefix Cache 命中率变化对性能影响有多大；
- 工具调用是否明显拉长端到端 SLA；
- 长稳测试中是否出现掉速、错误、OOM、eviction、preemption 或调度抖动。

国产化服务器测试的价值不只是证明“能跑”，而是要说明：

- 在什么 workload 下跑得最好；
- 性能边界在哪里；
- 哪些指标会先崩；
- 哪些优化手段有效；
- 哪些风险需要甲方线上复测时重点关注。

## 12. 最新结论摘要

梁老师最新输入说明，场景二不能再按普通 Agent 轻量交互来设计测试，而应按 **长上下文 Code/Search Agent serving** 来设计。

关键结论如下：

- P50 输入已经达到 32k tokens，属于明显长上下文场景；
- P99 输入达到 128k-256k tokens，必须验证国产化服务器在超长上下文下的能力；
- Max context 需要支持 262k tokens，这是硬性能力边界；
- 输出 P50 约 8k，P99 约 32k-64k，会显著增加 decode 占卡时间；
- 高并发下 P50 TTFT 目标是 10s 以内，P99 可放宽但必须记录；
- 高并发不要排队是关键要求，需要重点测试 Queue Delay；
- 当前参考 Prefix Cache Hit Rate 约 50%，但不同任务差异很大，需要分任务拆测；
- 测试重点应从“普通 TTFT/TPOT”升级为“长上下文 prefill、长输出 decode、KV Cache、Prefix Cache、Queue Delay 和长稳能力”。

一句话总结：

> 场景二的核心不是普通 Agent 并发测试，而是长上下文、多轮、Code/Search 型 Agent 在国产化服务器上的 serving 能力边界验证。
